# SLH-DSA-SHAKE-128s module

This directory contains a narrow C++20 wrapper and the minimum portable C
implementation needed for the FIPS 205 `SLH-DSA-SHAKE-128s` parameter set.
The wire sizes are fixed at a 32-byte public key, 64-byte secret key, and
7,856-byte signature.

## Provenance and license

The C implementation under `vendor/` was copied from
[`pq-code-package/slhdsa-c`](https://github.com/pq-code-package/slhdsa-c) at
commit `174c02e42257f95c210963272877c49dbb50070f`. The upstream license is
preserved verbatim in `LICENSE.upstream`; each vendored source retains its
SPDX declaration.

Only these upstream files were retained:

- `slh_dsa.c`, `slh_dsa.h`, `slh_shake.c`, `slh_param.h`, `slh_var.h`,
  `slh_adrs.h`, and `slh_sys.h`;
- `sha3_api.c`, `sha3_api.h`, and `sha3_f1600.c` for the exact FIPS 202 SHAKE
  implementation used by upstream;
- `plat_local.h` and `cbmc.h` support headers.

Syscoin modifications are marked in the affected files. They remove every
parameter instantiation except SHAKE-128s, reduce internal array bounds to
that parameter set, remove unused SHA-2 state, prefix externally visible C
symbols, make byte-order handling explicit and fail closed when it is unknown,
preserve canonical SHAKE lane bytes on big-endian targets, and cleanse
transient key-derived buffers. SHA-2, prehash, experimental parameters, test
drivers, and upstream build files are intentionally not vendored. A private
Syscoin adapter exposes only the pinned SHAKE-128s WOTS+ and tree-hash
primitives to the separately specified scheduled child profile; it does not
expand the public SLH-DSA API or alter global signatures.

The C++ wrappers, private adapter header, and local self-test are Syscoin code
under the repository's MIT license.

## API and invariants

Include `crypto/slhdsa/slhdsa.h`.

- `GenerateSecretKey()` requires exactly 48 bytes containing
  `SK.seed || SK.prf || PK.seed`.
- `ImportSecretKey()` requires exactly 64 bytes and recomputes the public root
  before accepting the encoding.
- `SecretKey` is move-only. Destruction, move-from, and replacement cleanse
  its storage. Exported copies remain the caller's responsibility.
- `SignDeterministic()` uses the FIPS 205 deterministic option.
- `SignHedged()` requires exactly 16 bytes of fresh additional randomness.
  The module deliberately does not choose an RNG for its caller.
- Both signing functions use the FIPS 205 pure-interface context. It is at
  most 255 bytes and should carry a stable protocol domain such as a distinct
  ChainLock, BTCC, or MNAUTH domain.
- `Verify()` rejects incorrect public-key/signature lengths and oversized
  contexts before invoking the verifier.

`selftest.cpp` exposes an explicit, module-local regression test. It freezes
the public key and SHAKE256 digest of a deterministic signature generated by
the pinned implementation, verifies a hedged signature, and checks mutation,
domain, truncation, oversized-context, and corrupt-secret-key failures. This
is regression coverage, not a replacement for NIST ACVP validation.

## Central and standalone checks

The module is part of Syscoin's central build and has unit, mutation, and fuzz
coverage through its wrapper and self-test. For a narrow build that does not
depend on the rest of the node, it can also be compiled from the repository
root:

```sh
SLH_BUILD_DIR="$(mktemp -d /tmp/syscoin-slhdsa.XXXXXX)"

for source in slh_dsa slh_shake sha3_api sha3_f1600; do
  cc -std=c99 -O2 -Wall -Wextra -Werror -Wpedantic \
    -Isrc/crypto/slhdsa/vendor \
    -c "src/crypto/slhdsa/vendor/${source}.c" \
    -o "${SLH_BUILD_DIR}/${source}.o"
done

for source in secure slhdsa selftest; do
  c++ -std=c++20 -O2 -Wall -Wextra -Werror -Wpedantic -Isrc \
    -c "src/crypto/slhdsa/${source}.cpp" \
    -o "${SLH_BUILD_DIR}/${source}.o"
done
```

A tiny executable may call `slhdsa::RunSelfTest()` and link those seven object
files. No object or generated file needs to be written into the source tree.

## Security status

The pinned upstream README calls `slhdsa-c` work in progress and explicitly
does not recommend relying on it for production-sensitive data before its
first stable release. This module therefore must remain gated from consensus
activation until the exact pinned implementation, Syscoin's minimization and
cleanup changes, deterministic/hedged transcript use, and platform builds have
received independent cryptographic review and NIST-vector testing.

SLH-DSA also does not aggregate signatures. Syscoin therefore reserves this
standardized profile for infrequent global operator authentication; live
ChainLock shares use the separately specified bounded-use child profile.
Every network path carrying a global signature must still impose explicit
message-size, admission, rate, and parallel-verification bounds.
